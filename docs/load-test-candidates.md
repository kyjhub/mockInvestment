# 부하 테스트 후보

이미 수행한 "트랜잭션 경계와 외부 API 호출 위치" 실험과 같은 틀로 측정해 볼 만한 항목을 모았다. 아직 실행하지 않았다.

## 기존 실험에서 가져온 틀

트랜잭션 경계 실험이 설득력을 가진 이유는 결과가 좋아서가 아니라 **구조** 때문이었다. 새 실험도 같은 구조를 따른다.

| 요소 | 트랜잭션 경계 실험에서의 모습 |
| --- | --- |
| **가설** | 외부 응답을 기다리는 동안의 커넥션 점유가 병목이다 |
| **한 변수만** | 같은 `matchOrder()`를 호출하고 외부 호출 위치만 트랜잭션 안/밖으로 |
| **변수 통제** | 계좌·종목을 주문마다 분리해 계좌 row 락 경합 제거, 스케줄 작업 중지 |
| **역검증** | 커넥션 풀만 10 → 25로 늘려 한계선이 함께 이동하는지 확인 → 병목 지목이 옳았음을 뒷받침 |
| **음성 대조** | 동시 요청이 풀 크기 이하일 때(스레드 5·10)는 차이가 없음 → 저부하에서는 드러나지 않는 문제임을 명시 |
| **측정 위생** | 워밍업 회차 제외, 전 주문의 체결 완료를 검증해 빈 루프 측정 방지 |

**프로덕션 코드를 바꾸지 않고 옛 구조를 테스트 코드로 재현**한 점도 그대로 가져간다. 그래야 "개선 후 코드로 개선 전을 측정했다"는 의심을 받지 않는다.

## 공통 실행 조건

- `benchmarkTest` task로 분리해 일반 test 실행에서 뺀다. 통과/실패를 가리는 test가 아니다
- `TransactionBoundaryBenchmarkSupport`의 기존 장치를 재사용한다 — 워밍업 제외, 스케줄 작업 중지, 체결 완료 검증
- 로컬 Docker PostgreSQL 기준값임을 결과에 명시한다. 운영에서 DB가 원격이면 왕복 지연이 붙는다
- **스케줄러를 새로 추가하면 `application-benchmark.yaml`에도 반드시 넣는다.** 이 프로파일은 스케줄 작업을 끄는 게 아니라 주기를 1시간으로 늘려 중화하는 방식이라, 목록에 빠진 스케줄러는 조용히 측정 구간에서 돈다. 특히 벤치마크 DB는 Testcontainers가 아니라 재사용되는 로컬 컨테이너라 이전 회차의 미체결 주문이 남고, 그것들은 직전 거래일 종료 이전 접수분이라 **당일 유효 주문 실효(§11.5)의 대상**이 된다. 중화하지 않으면 측정 도중 주문 row 락을 잡으며 대량으로 돈다

## ① 가용잔고를 저장하지 않고 집계하는 비용

**다른 후보와 성격이 다르다.** 개선 폭을 재는 실험이 아니라, 계획서에 가정으로 적어 둔 것을 측정으로 바꾸는 실험이다.

> `10-ledger-redesign-and-available-balance.md` — "계좌당 미체결 주문이 수십 건 수준이라고 가정하고 구속액을 매번 집계한다. 수천 건을 유지하는 사용 패턴이 나오면 저장 컬럼 + 대사 방식으로 바꿔야 한다."

**당일 유효 주문 실효(§11.5)가 들어오면서 이 가정의 성격이 바뀌었다.** 그 전에는 모든 주문이 사실상 GTC라 미체결 주문이 계좌에 무한히 쌓였고, 계좌당 수천 건은 시간이 지나면 도달하는 정상 상태였다. 지금은 거래일이 끝날 때마다 미체결분이 `EXPIRED`로 빠지므로, 집계 대상은 **한 거래일에 그 계좌가 낸 미체결 주문**으로 상한이 잡힌다.

그래서 이 실험의 높은 N 구간(1,000·10,000)은 "언젠가 도달할 정상 상태"가 아니라 **상한을 확인하는 스트레스 구간**으로 읽어야 한다. 결론 문장도 "실사용 분포"가 아니라 "하루치 주문 분포"를 기준으로 써야 한다.

### 가설

주문 접수마다 미체결 주문을 집계하는 비용은 현실적인 주문 수에서 무시할 만하고, 컬럼 방식이 유리해지는 한계선이 존재한다.

### 설계

| | |
| --- | --- |
| 변수 | 계좌당 미체결 주문 수 — 0 / 10 / 100 / 1,000 / 10,000 |
| 측정 | `placeOrder` p50·p99 지연, 초당 접수 건수 |
| 대조군 | 구속액을 컬럼에서 읽는 변형을 테스트 코드로 재현 |
| 역검증 | `idx_orders_account_side_status`를 제거하면 한계선이 앞당겨지는지 → 인덱스가 병목을 옮기는지 확인 |
| 음성 대조 | 미체결 0건에서 두 방식의 차이가 없어야 함 |

### 기대 결론 형태

"미체결 N건까지는 컬럼 방식 대비 지연 차이가 X ms 이내이고, M건을 넘으면 역전된다. 하루에 한 계좌가 내는 미체결 주문이 N건 이하이므로 해제 누락 위험이 없는 파생 방식을 유지한다."

### 값어치

"해제 코드가 없어 안전하다"는 설계 판단에 **"그리고 느리지도 않다"는 숫자**가 붙는다. 그리고 언제 바꿔야 하는지 기준선이 나온다.

## ② WebSocket 구독 종목의 호가 재조회 제거

### 가설

신선도 게이트(`receivedAt >= submittedAt`)는 드문 예외 경로가 아니라 **신규 주문의 상시 경로**여서, 매칭마다 외부 호출이 발생한다.

푸시 간격이 125~150ms인데 주문 접수와 매칭 시도 사이에 프레임이 끼지 않으면 무조건 REST로 떨어지기 때문이다.

### 설계

| | |
| --- | --- |
| 변수 | 게이트 방식 — 접수 시각 기준(옛 구조 재현) vs 구독 종목은 캐시 사용(현재) |
| 측정 | 스윕 1회당 Toss REST 호출 수, 스윕 소요시간, rate limiter 예산 소모 |
| 대조군 | 비구독 종목 — 두 방식에서 동일해야 함 |
| 역검증 | **오래된 주문**(30초 안전망이 재발행한 것)은 옛 방식에서도 호출이 없어야 함 |
| 음성 대조 | 호가 캐시가 이미 주문보다 신선한 경우 차이 없음 |

역검증이 이 실험의 핵심이다. "낡은 주문은 원래도 호출이 없었다"를 보이면 **신규 주문만 문제였다**는 진단이 정확했음이 드러난다.

### 기대 결론 형태

"신규 주문 50건 스윕에서 외부 호출 50회 → 0회. 실효 한도 초당 12회 기준으로 4초 이상 걸리던 스윕이 X ms로."

### 재현 비용

가장 낮다. 옛 게이트는 조건문 세 줄이라 테스트 코드로 그대로 재현된다.

## ③ 계좌 락 보유 시간이 주문 접수 지연에 미치는 영향

### 가설

매칭이 계좌 락을 오래 쥐면 **그 계좌 사용자의 주문 접수가 대기한다.** 접수도 계좌 row를 잠그기 때문이다(§13.11).

### 설계

| | |
| --- | --- |
| 변수 | 트랜잭션 경계 — 주문 단위(옛 구조 재현) vs 체결 단위(현재) |
| 측정 | 매칭이 도는 동안 해당 계좌들의 `placeOrder` p50·p99 |
| 대조군 | 매칭이 돌지 않을 때의 `placeOrder` 지연 (기준선) |
| 역검증 | 매칭과 무관한 계좌는 두 방식에서 차이가 없어야 함 |

### 기대 결론 형태

"10계좌·100주 체결 중 해당 계좌의 접수 p99가 62ms → 6ms. 매칭과 무관한 계좌는 두 구조 모두 기준선과 동일."

참고로 체결 소요는 이미 측정해 두었다 — 로컬 Docker PostgreSQL에서 1계좌·10주 9.4ms, 5계좌·50주 36.6ms, 10계좌·100주 62.4ms로 계좌당 약 6ms의 선형이다.

### 값어치와 비용

값어치가 가장 크다. **사용자에게 보이는 지표**(주문 버튼 응답)로 환산되기 때문이다.

다만 재현 비용도 가장 크다. 주문 단위 구조를 테스트 코드로 다시 만들어야 하고 — 참가 계좌를 미리 id 순으로 일괄 잠그고 한 트랜잭션에서 전부 체결하는 형태 — 그게 실제 옛 코드와 같다는 것을 설득해야 한다. 트랜잭션 경계 실험이 호출 위치만 바꾸면 됐던 것과 대조적이다.

## ④ 복식부기의 쓰기 비용 — **측정 완료 (2026-09-13)**

개선이 아니라 **대가를 재는** 실험이었다. 결론부터: **복식부기의 대가는 체결 1건의 3.1%다.** 지금 눈에 보이는 비용의 대부분은 복식부기가 아니라 **JDBC 배치가 꺼져 있어서** 생긴다.

### 측정 방법

재는 것은 **체결 1건의 회계 기록을 남기는 비용**이다. 매칭 로직은 다섯 변형 모두 건드리지 않는다. 모두 동기이고 모두 트랜잭션 안에서 쓴다. 다른 것은 **행 수**와 **DB 왕복 횟수**뿐이다.

| 변형 | 내용 | 왕복 |
| --- | --- | ---: |
| `SINGLE` | 단식 1행. 삭제된 `cash_transactions` 구조를 같은 모양의 표로 재현 | 1 |
| `DOUBLE_JPA` | **현재 운영 경로.** `LedgerPostingService.post()` — 거래 1행 + 분개 5행 | 6 |
| `DOUBLE_JPA_SEQ` | JPA 그대로, ID 전략만 `SEQUENCE`(pooled, allocationSize=50) + `batch_size` | 2 |
| `DOUBLE_JDBC` | 같은 6행을 JDBC로 한 건씩 | 6 |
| `DOUBLE_BATCH` | 같은 6행을 거래 1왕복 + 분개 배치 1왕복으로 | 2 |

`LedgerTransaction`·`LedgerEntry`가 `GenerationType.IDENTITY`라 **Hibernate가 JDBC 배치를 아예 못 한다.** 생성된 키를 INSERT 직후 받아야 하기 때문이다. `DOUBLE_JPA_SEQ`는 운영 엔티티를 건드리지 않으려고 같은 모양의 별도 표(`bench_ledger_*`)에 매핑한 테스트 전용 엔티티로 쟀다.

JDBC 변형은 `JdbcTemplate`이 아니라 `DataSourceUtils.getConnection()` + `PreparedStatement`다. `JdbcTemplate`이 트랜잭션 바인딩 커넥션을 얻는 방식과 같고 그 위에 예외 변환만 얹으므로, 수치는 `JdbcTemplate`에 그대로 전이된다.

**공정성 보정.** 첫 실행에서 `DOUBLE_JPA`만 `findById`로 Account·Stock을 조회해 SELECT 2번이 복식부기 몫으로 잘못 계상됐다(6.91x로 부풀었다). 실제 체결 경로에서는 두 엔티티가 이미 락과 함께 로드되어 있어 원장 쓰기의 비용이 아니다. `getReference`로 바꾸고 `Posting` record를 직접 만들어 SELECT를 없앴다.

### 결과

로컬 Docker PostgreSQL 17, 체결 500건, 분개 5줄, 단일 스레드 중앙값. 분모인 **체결 1건 전체 = 9,572us**는 내부 체결을 실제 매칭 경로로 100번 돌린 중앙값이다(외부 호출 없음).

| 변형 | 쓰기(us) | SINGLE 대비 | 체결 1건 중 비중 |
| --- | ---: | ---: | ---: |
| `SINGLE` | 395 | 1.00x | 4.1% |
| `DOUBLE_JPA` (현재) | 2,213 | 5.55x | **23.1%** |
| `DOUBLE_JPA_SEQ` | 728 | 1.85x | 7.6% |
| `DOUBLE_JDBC` | 1,399 | 4.30x | 14.6% |
| `DOUBLE_BATCH` | 688 | 1.75x | 7.2% |

```text
복식부기의 순수 대가   (SINGLE → DOUBLE_BATCH)     = +293 us   체결의  3.1%
현재 구조의 추가 비용 (DOUBLE_BATCH → DOUBLE_JPA)  = +1,525 us  체결의 15.9%

[선택지] JPA + SEQUENCE + 배치 : 체결 9,572 → 8,087 us  (처리량 1.18x)
[선택지] JDBC 배치            : 체결 9,572 → 8,047 us  (처리량 1.19x)
두 선택지의 차이 = 40 us (체결의 0.4%)
```

3회 반복에서 `DOUBLE_JPA_SEQ` 728/778/744us, `DOUBLE_BATCH` 688/696/599us로 차이가 40~145us에 머물렀다. threads=10에서도 2,495 vs 2,176us로 같은 관계다.

### 결론

**복식부기는 동기로 유지한다.** 전역 합계 검증과 실현손익 재계산을 얻는 대가가 체결의 3.1%다. 이 정도를 아끼려고 정합성을 내주는 건 말이 되지 않는다.

**비싼 건 복식부기가 아니라 `IDENTITY`다.** 체결 1건당 15.9%를 왕복 횟수에 쓰고 있다.

**`JdbcTemplate`은 성능 이유로는 선택할 근거가 없다.** 측정 전 추정은 "JPA 오버헤드는 배치와 무관하게 남으므로 JPA+SEQUENCE는 1,800us대에 착지한다"였는데 **틀렸다.** `DOUBLE_JPA`가 비쌌던 이유는 영속성 컨텍스트가 아니라 `IDENTITY`가 강제한 6번의 왕복이었다. 배치가 켜지면 JPA는 JDBC 배치와 0.4% 안쪽으로 붙는다.

**영속성 컨텍스트 OOM은 이 경로에 해당하지 않는다.** 대량 적재에서는 실재하는 문제지만, 여기서 한 트랜잭션이 다루는 엔티티 수는 **데이터량과 무관한 상수**다. 내부 체결 1건이 남기는 원장은 `ledger_transactions` 1행 + 분개 5행 = 6행이고, 영속성 컨텍스트 전체로 보면 여기에 주문 2, 계좌 2, 보유 2, 체결 2가 더해져 약 14개다. 원장이 길어져도, 계좌가 늘어도 이 수는 변하지 않는다.

쌓이지 않는 이유는 `matchOrder`가 **체결마다 트랜잭션을 새로 연다**는 데 있다(§13.2). 대량 주문이 상대 500명에게 체결되면 500개의 짧은 트랜잭션이 차례로 열리고 닫히지, 하나의 컨텍스트에 7,000개 엔티티가 쌓이지 않는다. 데드락 회피를 위해 도입한 건별 트랜잭션이 메모리 상한도 함께 보장하는 셈이다. 뒤집으면 **여러 체결을 한 트랜잭션에 묶는 변경을 하면 이 결론도 깨진다.**

그래서 체결 경로는 `SEQUENCE` + `batch_size`로 간다. `JdbcTemplate`은 **한 트랜잭션이 수천 행을 쓰는 작업**(대량 정정, 마이그레이션, 스냅샷 적재)에 남겨 둔다. 거기서는 메모리 상한이 실제 근거가 된다.

한 가지 더 — 지금 구조에서 `JdbcTemplate`은 비용이 따로 있다. INSERT 컬럼 목록을 손으로 유지해야 하므로 `LedgerEntry`에 컬럼을 더하고 SQL을 빠뜨리면 **그 컬럼이 조용히 기록되지 않는다.** 원장에서 조용한 누락은 복식부기가 막으려는 바로 그 종류의 버그다.

### 재현

## ⑤ 장 마감 직후 대량 실효의 소요 시간과 경합

### 가설

당일 유효 주문 실효(§11.5)는 건당 트랜잭션이라 안전하지만, **대상 건수에 상한이 없다.** `findExpirableOrderIds`는 `limit` 없이 대상 전부를 돌려주고 배치는 그걸 순차로 처리한다. 마감 직후 한 번에 수만 건이 걸리면 한 사이클이 길어지고, 그동안 같은 주문 row를 잠그는 매칭·취소와 경합한다.

경합 상대를 분명히 해두면 — **주문 접수는 직접 막히지 않는다.** 접수 시 구속액 집계(`sumReservedCash`)는 잠그지 않는 읽기라 PostgreSQL MVCC에서 쓰기와 부딪치지 않는다. 실제로 부딪치는 건 **같은 주문 row를 `FOR UPDATE`로 잡는 쪽**, 즉 매칭 엔진과 사용자 취소다. 그리고 마감 직후에는 이 경합이 실제로 일어난다. 어제 접수된 미체결 주문은 **실효 대상이면서 동시에 매칭 대상**이기 때문이다.

간접 경로로는 커넥션 풀이 있다. N건을 순차 트랜잭션으로 처리하면 그동안 커넥션 하나를 계속 잡았다 놓는다.

### 설계

| | |
| --- | --- |
| 변수 | 실효 대상 주문 수 — 100 / 1,000 / 10,000 / 100,000 |
| 측정 | 배치 전체 소요시간, 건당 p50·p99, 동시 진행 중인 매칭 처리량과 주문 취소 p99 |
| 대조군 | 현재 방식(건당 트랜잭션) vs 청크 1,000건 vs 단일 벌크 `UPDATE` |
| 역검증 | 매칭을 멈춘 상태와 돌리는 상태를 비교 → 느려진 원인이 정말 락 경합인지, 아니면 그냥 건수인지 |
| 음성 대조 | 실효 대상 0건일 때 매칭 처리량에 차이가 없어야 함 |

**fixture 주의.** `submittedAt`이 `@CreationTimestamp`라 대량 주문을 과거 시각으로 만들려면 저장 후 bulk update로 되돌려야 한다. `DayOrderExpiryIntegrationTest`가 쓰는 방식과 같다. 그리고 공통 실행 조건에 따라 벤치마크 프로파일에서 실효 스케줄러를 중화해 두었으므로, 이 실험은 스케줄러를 기다리지 말고 `expireDayOrders()`를 직접 호출한다.

### 기대 결론 형태

"N건 실효에 T초가 걸리고 그동안 매칭 처리량이 X% 떨어진다. 10만 건에서도 마감 직후 1분 안에 끝나므로 `limit` 없이 유지한다" — 또는 "M건을 넘으면 한 사이클이 실행 간격을 넘기므로 청크가 필요하다".

### 값어치

**`limit`이 없는 것이 의도인지 방치인지 판가름난다.** 지금은 "건당 트랜잭션이라 괜찮다"는 말만 있고 숫자가 없다.

벌크 `UPDATE` 한 방이면 훨씬 빠르지만, 그 대신 **락을 잡은 뒤 상태와 접수 시각을 다시 확인하는 단계를 잃는다.** 그 재확인이 매칭·취소와의 경합에서 정확성을 지키는 장치다(§11.5). 속도를 위해 그걸 버릴지 말지를 감이 아니라 숫자를 놓고 정할 수 있게 된다.

## 측정할 때 주의할 것

- **로컬 Docker PostgreSQL은 네트워크가 사실상 없다.** 운영에서 DB가 원격이면 왕복 지연이 붙어 모든 수치가 커진다. 결론은 절대값이 아니라 **비율과 한계선**으로 쓴다
- **워밍업을 반드시 버린다.** JIT와 커넥션 풀 초기화가 첫 회차를 왜곡한다
- **측정 대상 외의 스케줄 작업을 멈춘다.** dirty drain(150ms), 스트림 소비(100ms), 평가(60초)가 돌면 커넥션과 CPU를 가져간다
- **빈 루프를 재지 않는다.** 주문이 실제로 체결됐는지, 외부 호출이 실제로 나갔는지 검증한 뒤 시간을 기록한다
