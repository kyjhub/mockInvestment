# 부하 테스트 후보

이미 수행한 "트랜잭션 경계와 외부 API 호출 위치" 실험과 같은 틀로 측정해 볼 만한 항목을 모았다. 아직 실행하지 않았다.

## 기존 실험에서 가져온 틀

트랜잭션 경계 실험이 설득력을 가진 이유는 결과가 좋아서가 아니라 **구조** 때문이었다. 새 실험도 같은 구조를 따른다.

| 요소 | 트랜잭션 경계 실험에서의 모습 |
| --- | --- |
| **가설** | 외부 응답을 기다리는 동안의 커넥션 점유가 병목이다 |
| **한 변수만** | 같은 `matchOrder()`를 호출하고 외부 호출 위치만 트랜잭션 안/밖으로 |
| **변수 통제** | 계좌·종목을 주문마다 분리해 계좌 row 락 경합 제거, 스케줄 작업 중지 |
| **역검증** | 커넥션 풀만 10 → 25로 늘려 한계선이 함께 이동하는지 확인 → 병목 지목이 옳았음을 뒷받침 |
| **음성 대조** | 동시 요청이 풀 크기 이하일 때(스레드 5·10)는 차이가 없음 → 저부하에서는 드러나지 않는 문제임을 명시 |
| **측정 위생** | 워밍업 회차 제외, 전 주문의 체결 완료를 검증해 빈 루프 측정 방지 |

**프로덕션 코드를 바꾸지 않고 옛 구조를 테스트 코드로 재현**한 점도 그대로 가져간다. 그래야 "개선 후 코드로 개선 전을 측정했다"는 의심을 받지 않는다.

## 공통 실행 조건

- `benchmarkTest` task로 분리해 일반 test 실행에서 뺀다. 통과/실패를 가리는 test가 아니다
- `TransactionBoundaryBenchmarkSupport`의 기존 장치를 재사용한다 — 워밍업 제외, 스케줄 작업 중지, 체결 완료 검증
- 로컬 Docker PostgreSQL 기준값임을 결과에 명시한다. 운영에서 DB가 원격이면 왕복 지연이 붙는다
- **스케줄러를 새로 추가하면 `application-benchmark.yaml`에도 반드시 넣는다.** 이 프로파일은 스케줄 작업을 끄는 게 아니라 주기를 1시간으로 늘려 중화하는 방식이라, 목록에 빠진 스케줄러는 조용히 측정 구간에서 돈다. 특히 벤치마크 DB는 Testcontainers가 아니라 재사용되는 로컬 컨테이너라 이전 회차의 미체결 주문이 남고, 그것들은 직전 거래일 종료 이전 접수분이라 **당일 유효 주문 실효(§11.5)의 대상**이 된다. 중화하지 않으면 측정 도중 주문 row 락을 잡으며 대량으로 돈다

## ① 가용잔고를 저장하지 않고 집계하는 비용

**다른 후보와 성격이 다르다.** 개선 폭을 재는 실험이 아니라, 계획서에 가정으로 적어 둔 것을 측정으로 바꾸는 실험이다.

> `10-ledger-redesign-and-available-balance.md` — "계좌당 미체결 주문이 수십 건 수준이라고 가정하고 구속액을 매번 집계한다. 수천 건을 유지하는 사용 패턴이 나오면 저장 컬럼 + 대사 방식으로 바꿔야 한다."

**당일 유효 주문 실효(§11.5)가 들어오면서 이 가정의 성격이 바뀌었다.** 그 전에는 모든 주문이 사실상 GTC라 미체결 주문이 계좌에 무한히 쌓였고, 계좌당 수천 건은 시간이 지나면 도달하는 정상 상태였다. 지금은 거래일이 끝날 때마다 미체결분이 `EXPIRED`로 빠지므로, 집계 대상은 **한 거래일에 그 계좌가 낸 미체결 주문**으로 상한이 잡힌다.

그래서 이 실험의 높은 N 구간(1,000·10,000)은 "언젠가 도달할 정상 상태"가 아니라 **상한을 확인하는 스트레스 구간**으로 읽어야 한다. 결론 문장도 "실사용 분포"가 아니라 "하루치 주문 분포"를 기준으로 써야 한다.

### 가설

주문 접수마다 미체결 주문을 집계하는 비용은 현실적인 주문 수에서 무시할 만하고, 컬럼 방식이 유리해지는 한계선이 존재한다.

### 설계

| | |
| --- | --- |
| 변수 | 계좌당 미체결 주문 수 — 0 / 10 / 100 / 1,000 / 10,000 |
| 측정 | `placeOrder` p50·p99 지연, 초당 접수 건수 |
| 대조군 | 구속액을 컬럼에서 읽는 변형을 테스트 코드로 재현 |
| 역검증 | `idx_orders_account_side_status`를 제거하면 한계선이 앞당겨지는지 → 인덱스가 병목을 옮기는지 확인 |
| 음성 대조 | 미체결 0건에서 두 방식의 차이가 없어야 함 |

### 기대 결론 형태

"미체결 N건까지는 컬럼 방식 대비 지연 차이가 X ms 이내이고, M건을 넘으면 역전된다. 하루에 한 계좌가 내는 미체결 주문이 N건 이하이므로 해제 누락 위험이 없는 파생 방식을 유지한다."

### 값어치

"해제 코드가 없어 안전하다"는 설계 판단에 **"그리고 느리지도 않다"는 숫자**가 붙는다. 그리고 언제 바꿔야 하는지 기준선이 나온다.

## ② WebSocket 구독 종목의 호가 재조회 제거

### 가설

신선도 게이트(`receivedAt >= submittedAt`)는 드문 예외 경로가 아니라 **신규 주문의 상시 경로**여서, 매칭마다 외부 호출이 발생한다.

푸시 간격이 125~150ms인데 주문 접수와 매칭 시도 사이에 프레임이 끼지 않으면 무조건 REST로 떨어지기 때문이다.

### 설계

| | |
| --- | --- |
| 변수 | 게이트 방식 — 접수 시각 기준(옛 구조 재현) vs 구독 종목은 캐시 사용(현재) |
| 측정 | 스윕 1회당 Toss REST 호출 수, 스윕 소요시간, rate limiter 예산 소모 |
| 대조군 | 비구독 종목 — 두 방식에서 동일해야 함 |
| 역검증 | **오래된 주문**(30초 안전망이 재발행한 것)은 옛 방식에서도 호출이 없어야 함 |
| 음성 대조 | 호가 캐시가 이미 주문보다 신선한 경우 차이 없음 |

역검증이 이 실험의 핵심이다. "낡은 주문은 원래도 호출이 없었다"를 보이면 **신규 주문만 문제였다**는 진단이 정확했음이 드러난다.

### 기대 결론 형태

"신규 주문 50건 스윕에서 외부 호출 50회 → 0회. 실효 한도 초당 12회 기준으로 4초 이상 걸리던 스윕이 X ms로."

### 재현 비용

가장 낮다. 옛 게이트는 조건문 세 줄이라 테스트 코드로 그대로 재현된다.

## ③ 계좌 락 보유 시간이 주문 접수 지연에 미치는 영향

### 가설

매칭이 계좌 락을 오래 쥐면 **그 계좌 사용자의 주문 접수가 대기한다.** 접수도 계좌 row를 잠그기 때문이다(§13.11).

### 설계

| | |
| --- | --- |
| 변수 | 트랜잭션 경계 — 주문 단위(옛 구조 재현) vs 체결 단위(현재) |
| 측정 | 매칭이 도는 동안 해당 계좌들의 `placeOrder` p50·p99 |
| 대조군 | 매칭이 돌지 않을 때의 `placeOrder` 지연 (기준선) |
| 역검증 | 매칭과 무관한 계좌는 두 방식에서 차이가 없어야 함 |

### 기대 결론 형태

"10계좌·100주 체결 중 해당 계좌의 접수 p99가 62ms → 6ms. 매칭과 무관한 계좌는 두 구조 모두 기준선과 동일."

참고로 체결 소요는 이미 측정해 두었다 — 로컬 Docker PostgreSQL에서 1계좌·10주 9.4ms, 5계좌·50주 36.6ms, 10계좌·100주 62.4ms로 계좌당 약 6ms의 선형이다.

### 값어치와 비용

값어치가 가장 크다. **사용자에게 보이는 지표**(주문 버튼 응답)로 환산되기 때문이다.

다만 재현 비용도 가장 크다. 주문 단위 구조를 테스트 코드로 다시 만들어야 하고 — 참가 계좌를 미리 id 순으로 일괄 잠그고 한 트랜잭션에서 전부 체결하는 형태 — 그게 실제 옛 코드와 같다는 것을 설득해야 한다. 트랜잭션 경계 실험이 호출 위치만 바꾸면 됐던 것과 대조적이다.

## ④ 복식부기의 쓰기 비용

개선이 아니라 **대가를 재는** 실험이다.

| | |
| --- | --- |
| 가설 | 복식부기는 체결당 행 수를 늘려 체결 처리량을 떨어뜨린다 |
| 변수 | 체결 1건당 기록 — 단식 1행(옛 구조 재현) vs 복식 `ledger_transactions` 1 + `ledger_entries` 2~5행 |
| 측정 | 체결 처리량, 체결 1건 소요시간 |
| 음성 대조 | 체결이 없는 주문(유동성 부족)에서는 차이 없음 |

결론 형태: "체결 처리량이 X% 감소했으나, 그 대가로 전역 합계 검증과 실현손익 재계산이 가능해졌다."

**숫자가 나쁘게 나와도 그대로 적는다.** 트레이드오프를 알고 선택했다는 기록이 목적이다.

## 우선순위

| 순위 | 후보 | 이유 |
| --- | --- | --- |
| 1 | **① 가용잔고 집계 비용** | 검증되지 않은 가정을 없앤다. 기존 실험이 "성능 개선"이라면 이건 "설계 검증"이라 성격이 겹치지 않는다 |
| 2 | **② 호가 재조회 제거** | 투입 대비 산출이 가장 좋다. 재현이 세 줄, 측정 지표가 명확, 역검증 설계가 깔끔 |
| 3 | **③ 락 보유 시간** | 값어치는 크지만 옛 구조 재현 비용이 높다 |
| 4 | **④ 복식부기 비용** | 보너스. 앞의 셋을 하고 여유가 있을 때 |

## 측정할 때 주의할 것

- **로컬 Docker PostgreSQL은 네트워크가 사실상 없다.** 운영에서 DB가 원격이면 왕복 지연이 붙어 모든 수치가 커진다. 결론은 절대값이 아니라 **비율과 한계선**으로 쓴다
- **워밍업을 반드시 버린다.** JIT와 커넥션 풀 초기화가 첫 회차를 왜곡한다
- **측정 대상 외의 스케줄 작업을 멈춘다.** dirty drain(150ms), 스트림 소비(100ms), 평가(60초)가 돌면 커넥션과 CPU를 가져간다
- **빈 루프를 재지 않는다.** 주문이 실제로 체결됐는지, 외부 호출이 실제로 나갔는지 검증한 뒤 시간을 기록한다
