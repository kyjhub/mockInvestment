# 시가 평가 batch

## Context

10번 계획을 마치면서 일별 스냅샷(C-14)을 보류했다. 이유는 필요 없어서가 아니라 **시가 평가가 없어서**였다. 지금 막혀 있는 것이 셋이다.

| 막힌 것 | 상태 |
| --- | --- |
| `Account.total_asset_value` | 체결이 갱신하지 않아 실제 자산과 무관한 값이다 (§19.2) |
| `DailyAccountSnapshot` | `stock_evaluation`·`unrealized_profit`·`return_rate`가 not null인데 셋 다 시가를 요구한다 |
| `LeaderboardRanking` | 수익률 순위가 이 서비스의 핵심인데, 수익률은 시점 간 평가액 차이라 스냅샷 없이는 나오지 않는다 |

평가 batch 하나가 이 셋을 한꺼번에 여는 길목이다.

### 평가액은 원장 파생이 아니다

이 구분이 설계 전체를 가른다. 지금까지 만든 잔고·보유·실현손익은 전부 원장에서 재계산해 검증할 수 있었다(§13.11). **평가액은 그럴 수 없다.** 시가는 외부에서 온 데이터고, 같은 보유라도 어제와 오늘 값이 다르다.

따라서:

- `stock_evaluation`, `unrealized_profit`, `total_asset_value`는 **대사 대상이 아니다.** 비교할 기준이 원장에 없다.
- 대신 그 입력인 **보유 수량과 예수금은 원장 파생**이므로 대사할 수 있다. 평가를 확정하기 전에 그쪽을 먼저 검증하면 된다(5.2).

### 두 가지 용도를 섞지 않는다

"평가"라는 한 단어에 성격이 다른 두 요구가 들어 있다.

| | 실시간 총자산 | 마감 확정 |
| --- | --- | --- |
| 소비자 | 사용자 화면의 총자산 | 스냅샷, 리더보드, 수익률 |
| 필요한 것 | 지금 값. 몇 분 낡아도 된다 | **그날의 확정값.** 나중에 물어봐도 같아야 한다 |
| 가격 원천 | 현재가(`lastPrice`) | **종가(candle close)** |
| 주기 | 분 단위 | 영업일 1회 |
| 틀렸을 때 | 다음 주기에 고쳐진다 | 규제·순위 산출이 어긋난다 |

한 batch로 묶으면 둘 다 어중간해진다. 계산 로직은 공유하고 **일정과 가격 원천만 나눈다.**

## 범위 조정 (2026-09-12)

리더보드를 **자본금 리그 + 시즌제 단순 수익률**로 정하고 구현은 운영 중 도입으로 미뤘다(12번). 이 결정이 이 계획의 범위를 줄인다.

| 절 | 상태 | 사유 |
| --- | --- | --- |
| 1·2·3.1·4 실시간 평가 | **이번에 구현** | 잔고 화면의 평가손익률과 `total_asset_value`가 여기 걸려 있다 |
| 6-1 잔고 API 확장 | **이번에 구현** | 서비스 사용에 바로 필요하다 |
| 3.2·3.3 종가 조회 | 보류 | 마감 스냅샷 전용이다 |
| 5 마감 스냅샷 | 보류 | 아래 참고 |

**마감 스냅샷을 보류하는 이유**: 원래 목적이 리더보드의 TWR 연쇄 입력이었다. 시즌제 단순 수익률은 `현재 총자산`과 `시즌 시작 자본`만 있으면 되므로 일별 연쇄가 필요 없다. 자산 추이 그래프처럼 다른 소비자가 생기면 그때 다시 본다. 5.3(`balance_after` 검증)과 5.4(수익률 정의)도 함께 미뤄진다.

보류한 절은 지우지 않고 남겨 둔다. 필요해질 때 설계를 다시 하지 않기 위해서다.

## 1. 평가 계산

```text
종목 평가액   = holdings.quantity × 평가가격
계좌 평가액   = Σ(종목 평가액)
총자산       = accounts.cash_balance + 계좌 평가액
미실현손익    = 계좌 평가액 − Σ(holdings.total_purchase_amount)
```

`quantity = 0`인 보유 row는 건너뛴다. 매도로 0이 된 뒤 남아 있는 행이라 평가 대상이 아니다.

평가가격을 구하지 못한 종목이 하나라도 있으면 **그 계좌의 평가를 만들지 않는다.** 일부 종목만 반영한 총자산은 틀린 값이고, 틀린 값을 보여주는 것보다 "계산 중"이 낫다. 어느 종목 때문인지 로그로 남긴다.

## 2. 통화 — 지금은 단일 통화, 다만 가드를 박는다

`Stock`에는 `currency`가 있지만 **`Account`에는 통화 개념이 없다.** `cash_balance`가 무슨 통화인지 스키마가 말하지 않는다.

지금은 국내 종목 마스터 적재가 미구현이라 거래 가능한 종목이 전부 미국 주식(USD)이고, 그래서 사실상 단일 통화다. 이 전제 위에서는 환율 없이 평가가 성립한다.

문제는 국내 종목이 들어오는 순간 **조용히 틀린 값이 나온다**는 것이다. USD 평가액과 KRW 예수금을 그냥 더하게 된다.

그래서 전제를 주석이 아니라 **코드 가드**로 박는다.

```java
// 계좌의 보유 종목 통화가 둘 이상이면 환산 없이 더할 수 없다.
// 환율이 들어오기 전까지 이 경우는 평가를 만들지 않고 드러낸다.
Set<String> currencies = holdings.stream().map(h -> h.getStock().getCurrency()).collect(toSet());
if (currencies.size() > 1) {
    log.error("Cannot value a multi-currency account without FX. accountId={}, currencies={}", ...);
    return ValuationResult.skipped(account);
}
```

`ExchangeRate` 엔티티는 있지만 적재 client가 없다(§18). 진짜 해법 — 계좌에 기준통화를 두고 환산 — 은 환율 client와 함께 별도 계획으로 다룬다.

## 3. 가격 원천

### 3.1 실시간 총자산 — `PriceService.getPrices()`

이미 배치 조회다. 캐시에 없는 종목만 모아 **한 번의 Toss 호출**로 가져온다.

```java
PriceResponse prices = priceService.getPrices(distinctSymbols);   // lastPrice
```

보유 종목 수가 수백이어도 호출은 캐시 미스 묶음 하나다. 캐시 TTL이 2초라 미스가 잦지만, 분 단위 주기면 종목당 분당 1회 수준이다.

### 3.2 마감 확정 — `TossCandleClient.getLatestDailyCandle()`

**종가를 써야 한다.** `lastPrice`는 "조회한 순간의 값"이라 batch가 몇 시에 돌았는지에 따라 결과가 달라진다. 마감 확정값이 실행 시각에 좌우되면 "나중에 물어봐도 같아야 한다"가 깨진다.

```java
Candle candle = tossCandleClient.getLatestDailyCandle(symbol).result()...;
BigDecimal closePrice = candle.closePrice();
```

대신 **종목당 1콜**이다. `market-data-chart` 그룹 한도가 초당 20, 안전마진 0.8을 적용하면 실효 16회/초다. 보유 종목 500개면 약 31초. 하루 한 번이므로 감당 가능하지만 `TossApiRateLimiter`를 통과하도록 하고, 예산 소진 시 쿨다운을 기다렸다 이어서 한다.

**중복 제거가 중요하다.** 계좌마다 부르는 것이 아니라 전체 보유의 **distinct 종목**을 한 번 조회해 map으로 들고 계좌들을 순회한다. 계좌가 1만 개여도 호출 수는 종목 수에 묶인다.

### 3.3 캔들 날짜 확인

`getLatestDailyCandle`은 "가장 최근 일봉"이라 휴장 직후에는 전일 것이 온다. 반환된 `candle.timestamp()`의 날짜가 **마감하려는 영업일과 같은지 확인**하고, 다르면 그 종목을 미확보로 처리한다. 확인하지 않으면 휴장일 종가로 스냅샷을 만들게 된다.

## 4. 실시간 총자산 갱신

```java
@Scheduled(fixedDelayString = "${valuation.total-asset.fixed-delay-ms:60000}")
public void refreshTotalAssetValue()
```

보유가 있는 계좌만 대상으로 `accounts.total_asset_value`를 갱신한다.

- 계좌 row lock을 잡지 않는다. 이 값은 표시용이고, 체결과 경합해 잠깐 어긋나도 다음 주기에 맞는다. 락을 잡으면 평가 batch가 체결을 막는다.
- `cash_balance`는 읽기만 한다. 평가는 예수금을 바꾸지 않는다.
- 전용 scheduler(`SchedulingConfig`)를 하나 더 두어 매칭·WebSocket 작업과 격리한다. 계좌 수에 비례하는 작업이라 기본 풀에 두면 다른 주기 작업을 밀어낸다.

## 5. 마감 스냅샷

```java
@Scheduled(cron = "${valuation.daily-close.cron:0 0 7 * * *}")
public void closeDaily()
```

### 5.1 영업일 판정

`MarketCalendarService.getUsMarketCalendar(date)`로 대상일이 미국 정규장 영업일인지 확인하고, 아니면 스냅샷을 만들지 않는다. 휴장일 행을 만들면 수익률 연쇄(5.4)에 변동 없는 구간이 끼어 계산만 복잡해진다.

**실행 시각**: 미국 정규장 마감 16:00 ET는 서머타임에 따라 KST 05:00(EDT) 또는 06:00(EST)이다. 07:00 KST면 둘 다 지난 뒤다.

> 기존 대사 batch가 05:30 KST인데, 겨울(EST)에는 아직 장중이다. 읽기 전용 단일 transaction이라 잘못된 보고가 나오지는 않지만, 마감 스냅샷보다 **뒤에** 도는 것이 순서상 맞다. `ledger.reconciliation.cron`을 07:30으로 옮긴다.

### 5.2 대사를 통과한 계좌만 확정한다

**마감은 확정이다. 틀린 값을 확정 저장하면 안 된다.**

스냅샷을 만들기 전에 `LedgerReconciliationService.reconcile()`을 한 번 돌리고, 불일치 목록에 든 계좌는 **건너뛴다.**

```java
LedgerReconciliationReport report = reconciliationService.reconcile();
...
if (report.cashBalanceMismatchAccountIds().contains(accountId)
    || report.realizedProfitMismatchAccountIds().contains(accountId)) {
    log.error("Skipping daily close for an account that failed reconciliation. accountId={}", accountId);
    continue;
}
```

평가액 자체는 대사할 수 없지만(Context 참고), **그 입력인 예수금·보유·실현손익은 원장 파생이라 검증할 수 있다.** 입력이 틀린 채로 곱하면 평가액도 틀린다.

### 5.3 `balance_after` 검증을 여기에 넣는다

`ledger_entries.balance_after`는 비정규화 값인데 지금 아무도 확인하지 않는다. 계좌별로 분개를 시간순으로 재생하며 누적을 맞춰봐야 해서 계좌당 O(n)이라, 고정 개수 aggregate로 끝나는 §13.11 대사와 성격이 다르다.

하루 한 번 도는 이 batch가 그 자리다. 대상은 **직전 스냅샷 이후의 분개**로 한정하면 매일 일정한 양만 검사한다 — 스냅샷이 있는 이유 중 하나가 이것이다.

### 5.4 `return_rate` 정의 — 결정이 필요하다

스냅샷의 `return_rate`(precision 10,6)를 무엇으로 채울지 정해야 한다. 리더보드의 `cumulative_return_rate`가 여기서 나온다.

**(가) 단순 수익률** = `(총자산 − 투입원금) / 투입원금`, 투입원금 = `initial_balance + Σ(승인 충전액)`

간단하지만 **경쟁에서 불공정하다.** 자산을 1,000에서 2,000으로 불린 사람(+100%)이 1,000을 충전하면 자산 3,000 / 원금 2,000이 되어 +50%로 떨어진다. 돈을 넣었다고 수익률이 반토막 나는 것은 실력 순위로 쓸 수 없다.

**(나) 시간가중수익률(TWR)** — 현업 표준. 현금흐름의 영향을 제거한다.

```text
일간 수익률  r_d = (기말 총자산 − 당일 순입금) / 기초 총자산 − 1
누적 수익률       = Π(1 + r_d) − 1
```

일별 스냅샷이 바로 이 계산의 입력이다. 그리고 **당일 순입금을 원장이 정확히 준다** — `Σ(EQUITY_FUNDING entries)` 중 그날 것. 복식부기를 도입한 덕에 따로 집계할 필요가 없다.

**(나)를 권한다.** 리더보드가 이 서비스의 핵심이고, (가)로는 순위가 실력을 반영하지 못한다. 계산 입력도 이미 다 갖춰져 있다.

이 경우 스냅샷의 `return_rate`에는 **일간 수익률**을 넣는다. 누적은 리더보드 batch가 연쇄로 만든다. 일간 값이 합성 가능한 최소 단위이기 때문이다.

> **계좌 초기화와의 관계**: `Account.current_round`와 `AccountReset`이 있고 초기화 시 누적을 어떻게 다룰지는 01번 계획 소관이다. 라운드가 바뀌면 연쇄를 끊는지, 라운드별로 따로 쌓는지 먼저 정해야 리더보드가 완성된다. 이 계획은 **일간 수익률까지만** 책임진다.

### 5.5 재실행

`daily_account_snapshots`에 `(account_id, snapshot_date)` unique 제약이 있다. 배치가 두 번 돌거나 실패 후 재시도할 수 있으므로, 이미 있는 날짜는 **건너뛴다**(덮어쓰지 않는다). 마감은 확정이고, 다시 계산해야 한다면 그건 사람이 판단할 일이다.

## 6-1. 잔고 조회 API 확장

현업 증권사 잔고 화면은 **예수금을 수익률 분모에 넣지 않는다.** 분모는 총매입금액이다. 리더보드 수익률(예수금 포함, 12번)과 기준이 다른데, 이는 두 화면이 다른 질문에 답하기 때문이다.

| 화면 | 지표 | 분모 | 질문 |
| --- | --- | --- | --- |
| 잔고 | 평가손익률 | 총매입금액 | 지금 들고 있는 게 어떤가 |
| 리더보드 | 수익률 | 시즌 시작 자본 | 투자를 잘 하고 있나 |

`AccountBalanceResponse`에 다음을 추가한다.

```java
totalPurchaseAmount      // 총매입금액. Σ(holdings.total_purchase_amount)
stockEvaluation          // 주식 평가금액. Σ(수량 × 현재가)
unrealizedProfit         // 평가손익 = 평가금액 − 총매입금액
unrealizedProfitRate     // 평가손익률 = 평가손익 / 총매입금액
totalAsset               // 총자산 = 예수금 + 평가금액
```

`totalPurchaseAmount`는 지금도 원장에서 나온다. 시세가 필요한 것은 `stockEvaluation`부터다.

**총매입금액이 0이면 `unrealizedProfitRate`는 `null`이다.** 0으로 나눌 수 없고 0%도 아니다 — 보유가 없으면 수익률이라는 개념 자체가 없다.

**이름을 구분한다.** 두 수익률이 같은 이름이면 사용자가 버그로 신고한다. 잔고는 "평가손익률", 리더보드는 "수익률"로 부른다. 현업 관행이기도 하다.

## 6. `Account.total_asset_value`와 스냅샷의 관계

둘은 같은 계산이지만 값이 다를 수 있다. 실시간 쪽은 현재가, 마감 쪽은 종가다. **마감 스냅샷이 `total_asset_value`를 덮어쓰지 않는다** — 장이 열리면 실시간 쪽이 다시 갱신하므로 의미가 없고, 확정값은 스냅샷 테이블에 있다.

## 설정 추가

```yaml
valuation:
  total-asset:
    fixed-delay-ms: ${VALUATION_TOTAL_ASSET_DELAY_MS:60000}
  daily-close:
    # 미국 정규장 마감(16:00 ET)은 서머타임에 따라 KST 05:00 또는 06:00이다.
    cron: ${VALUATION_DAILY_CLOSE_CRON:0 0 7 * * *}
  scheduler:
    pool-size: ${VALUATION_SCHEDULER_POOL_SIZE:1}

ledger:
  reconciliation:
    # 마감 스냅샷보다 뒤에 둔다.
    cron: ${LEDGER_RECONCILIATION_CRON:0 30 7 * * *}
```

## 구현 순서

1. `ValuationService` 신설 — 평가 계산과 통화 가드(1·2절). 가격 map을 인자로 받아 시세 조회와 분리한다. 그래야 단위 test가 외부 없이 돈다.
2. `HoldingRepository`에 `quantity > 0`인 보유 조회와 distinct 종목 조회 추가.
3. 전용 scheduler를 `SchedulingConfig`에 추가.
4. `TotalAssetValuationScheduler` — 실시간 갱신(4절).
5. `DailyCloseService` — 영업일 판정, 대사 통과 확인, 종가 조회, 스냅샷 저장(5절).
6. `balance_after` 검증을 마감 batch에 추가(5.3).
7. `ledger.reconciliation.cron`을 07:30으로 이동.
8. 문서 갱신 — §19.2 해소, §18에서 해당 항목 제거.

1·2번까지 하면 평가 로직이 test 가능해지고, 4번과 5번은 서로 독립이라 나눠 머지할 수 있다.

## 검증 방법

**평가 계산**

- 보유 2종목(수량·단가 다름)의 총자산이 `예수금 + Σ(수량×가격)`과 일치하는지.
- 미실현손익이 `평가액 − Σ(취득원가)`와 일치하는지.
- `quantity = 0`인 보유 row가 계산에서 빠지는지.
- **한 종목의 가격을 못 구하면 그 계좌 평가가 통째로 생략되는지.** 일부만 반영된 총자산이 저장되면 안 된다.

**통화 가드**

- USD 종목과 KRW 종목을 함께 보유한 계좌가 평가에서 제외되고 ERROR가 남는지. 국내 종목이 들어왔을 때 조용히 틀리지 않는다는 것이 이 test의 요지다.

**마감**

- 휴장일에는 스냅샷이 생기지 않는지.
- 같은 날짜로 두 번 돌려도 행이 하나인지(재실행).
- **대사 불일치 계좌는 스냅샷이 만들어지지 않는지.** 잔고를 원장 없이 조작한 뒤 마감을 돌려 확인한다.
- 캔들 날짜가 대상 영업일과 다르면 그 종목이 미확보로 처리되는지.

**수익률**

- 순입금이 0인 날의 일간 수익률이 `기말/기초 − 1`인지.
- **충전이 있던 날의 일간 수익률이 충전액에 영향받지 않는지.** (가)와 (나)를 가르는 핵심 검증이다.

**호출량**

- 계좌 1,000개가 같은 종목 10개를 보유할 때 종가 조회가 10회인지. 계좌 수에 비례하면 안 된다.

## 추가할 자동화 테스트

- 총자산 = 예수금 + Σ(수량 × 가격)
- 미실현손익 = 평가액 − 취득원가 합계
- 가격 미확보 종목이 있으면 계좌 평가를 생략하는지
- 다중 통화 계좌가 제외되는지
- 휴장일에 스냅샷을 만들지 않는지
- 같은 날짜 재실행이 행을 늘리지 않는지
- 대사 불일치 계좌를 건너뛰는지
- 캔들 날짜가 대상일과 다르면 미확보로 처리하는지
- 일간 수익률이 당일 순입금의 영향을 받지 않는지
- distinct 종목 수만큼만 시세를 조회하는지
- 실시간 갱신이 `cash_balance`를 건드리지 않는지

## 이번 범위에서 제외

- **환율 client와 다중 통화 평가** — `ExchangeRate` 엔티티는 있으나 적재 경로가 없다(§18). 계좌에 기준통화를 두는 스키마 결정이 선행되어야 한다. 2절의 가드가 그때까지의 안전장치다.
- **리더보드 batch** — 12번으로 분리했고 운영 중 도입한다.
- **마감 스냅샷과 종가 조회** — 범위 조정 참고. 5절과 3.2·3.3은 보류다.
- **누적 수익률의 라운드 처리** — 5.4의 각주 참고.
- **과거 일자 소급 생성** — 스냅샷이 없는 과거 날짜를 만들려면 그 날의 종가가 필요한데, `getLatestDailyCandle`은 최신 1건만 준다. 기간 조회 API가 필요하다.
- **평가액의 대사** — 원장 파생이 아니므로 비교할 기준이 없다. 입력(예수금·보유)만 대사한다.

## 확인이 필요한 가정

- **`getLatestDailyCandle`이 마감 직후 그날 종가를 준다**고 가정했다. 공급자가 확정 종가를 언제 반영하는지 확인해야 한다. 늦게 반영되면 07:00 실행이 전일 값을 가져오고, 3.3의 날짜 확인에 걸려 그날 스냅샷이 통째로 비게 된다. 실측이 필요하고, 늦다면 실행 시각을 뒤로 미뤄야 한다.
- **보유 종목 수가 수백 수준**이라고 가정하고 종가를 종목당 1콜로 받는다. 수천으로 늘면 마감 batch가 분 단위로 길어져 rate limiter 쿨다운과 얽힌다. 기간·다종목 캔들 API가 있는지 확인이 필요하다.
- **모든 거래가 미국 시장**이라고 가정하고 영업일 판정에 `getUsMarketCalendar`만 쓴다. 국내 종목이 들어오면 시장별로 마감 시각과 영업일이 달라져 배치 구조 자체를 다시 봐야 한다.
- **`total_asset_value`가 몇 분 낡아도 된다**고 보고 락 없이 갱신한다. 이 값으로 주문 가능 여부 같은 판정을 하게 되면 전제가 깨진다. 판정에는 `cash_balance`와 §13.10의 주문가능금액을 쓴다.
